# Обновление Sfery 1.44.0 → 1.45.0

Кандидат обновления. Workflow собирает установщик, проверяет его в одноразовом профиле GitHub Actions и сохраняет артефакты. Релизы автоматически не публикуются.

## Данные

Производственная сборка использует прежние `Sfery`, `local-planner.exe`, идентификатор `local.sfery.planner`, издателя `sfery` и установку для текущего пользователя. База остаётся в `%APPDATA%\local.sfery.planner`, профиль WebView — в `%LOCALAPPDATA%\local.sfery.planner`. Данные отдельной Sfery Recovered автоматически не объединяются с обычной Sfery.

Перед первым открытием существующей базы создаётся `backups/pre-update-1.45.0-<UUID>` внутри прежней папки данных. SQLite Backup API включает подтверждённые записи WAL. Копируются вложения и остальные файлы, кроме прежних резервных копий и временных блокировок. Manifest содержит SHA-256 и размеры. Незавершённая копия получает `.partial` и не разрешает миграцию. Изменения схемы выполняются транзакционно; повреждённая база или версия схемы выше 9 отклоняется.

Повторный запуск открывает существующее окно. Дополнительно блокируется параллельное открытие той же папки данных и проверяется процесс обычной Sfery. Старую версию нужно закрыть перед обновлением. Поведение старой версии при повторном запуске во время работы новой отдельно не гарантируется.

`cloud-device.bin` читается через DPAPI текущего пользователя Windows, без перезаписи: поддержаны строка токена и JSON с полем token. Реальная облачная синхронизация требует ручной проверки перед массовым выпуском. Telegram использует восстановленный формат сессии: потребуется повторный вход, прежние файлы сохраняются в резервной копии. Алгоритм отбора Telegram-поручений реконструирован и может отличаться от исходного.

## Сборка

Нужны Node 24, Rust 1.99.1 MSVC и Microsoft C++ Build Tools. Из папки desktop запустить `./build-update.ps1` в PowerShell 7. Он проверяет подпись публичного установщика 1.44.0 и SHA-256 извлечённого EXE, выполняет тесты, собирает NSIS без devtools. Результат: `dist/update-1.45.0`.

Actions дополнительно устанавливает оригинал в одноразовом профиле runner, открывает синтетическую базу, обновляет существующую установку через `/UPDATE`, сравнивает задачи и тему после запуска 1.45.0. Проверяются путь базы, новая версия в реестре, резервная копия и сохранённый старый EXE. Личные базы и ключи владельца в репозиторий не включаются.

## Подпись и выпуск

Нужен прежний ключ, соответствующий публичному ключу в `tauri.production.conf.json`. Не создавать замену для существующих установок. Приватный ключ не добавлять в Git или сообщения.

```powershell
./sign-update.ps1 -Installer ./dist/update-1.45.0/Sfery_1.45.0_x64-setup.exe -KeyPath C:/path/to/existing.key
```

Пароль передаётся через `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. В Actions используются secrets `TAURI_SIGNING_PRIVATE_KEY` и `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` только при ручном запуске с sign=true. Проверка Minisign/Ed25519 подтверждает соответствие подписи прежнему публичному ключу. После неё создаётся latest.json. Сама подпись обновлений не является подписью Windows Authenticode.

Перед массовым выпуском проверить реальный вход Telegram и облачный обмен. Затем подготовить релиз v1.45.0 с установщиком, его `.sig` и `latest.json`. Публикация latest.json переводит обычную Sfery на новую версию; до готовности его не публиковать. Для ручного обновления запускать установщик с `/UPDATE`, сохраняя прежний путь установки.

## Откат

При обновлении через `/UPDATE` старый EXE сохраняется в `%LOCALAPPDATA%\local.sfery.planner\rollback\1.44.0`. Перед откатом закрыть Sfery и сделать отдельную копию текущих данных. Восстановить прежний EXE и файлы выбранной проверенной резервной копии, кроме manifest.json, в прежнюю папку данных. Остаточные `planner.sqlite-wal`/`planner.sqlite-shm` нельзя оставлять рядом с восстановленной базой. Откат базы возвращает состояние на момент копирования, поэтому последующие изменения сначала сохранить отдельно. Автоматическое перезаписывание данных при откате не реализовано.
