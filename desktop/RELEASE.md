# Восстановленная Sfery 1.45.0: переход с 1.44.0

Кандидат обновления. Workflow собирает установщик, проверяет его в одноразовом профиле GitHub Actions и сохраняет артефакты. Релизы автоматически не публикуются.

## Первый переход выполняется вручную

Прежний приватный ключ утрачен. Автообновление обычной 1.44.0 нельзя подписать новым ключом: установленный клиент доверяет только прежнему публичному ключу. Поэтому первый переход выполняется установщиком в режиме `/UPDATE`, с сохранением прежней установки и данных. Дальнейшие обновления восстановленной версии используют новый ключ и `latest-v2.json`.

Прежний `latest.json` из релиза 1.44.0 сохраняется без изменений и включается в новые релизы. Обычная Sfery видит свою последнюю версию 1.44.0, а восстановленная проверяет отдельный канал. Нельзя подменять старый latest.json манифестом с новой подписью.

## Совместимость данных

Производственная сборка сохраняет `Sfery`, `local-planner.exe`, идентификатор `local.sfery.planner`, издателя `sfery` и установку для текущего пользователя. База остаётся в `%APPDATA%\local.sfery.planner`, профиль WebView — в `%LOCALAPPDATA%\local.sfery.planner`. Данные отдельной Sfery Recovered автоматически не объединяются с обычной Sfery.

Перед первым открытием базы создаётся `backups/pre-update-1.45.0-<UUID>` в прежней папке данных. SQLite Backup API включает подтверждённые записи WAL. Копируются вложения и остальные файлы, кроме прежних резервных копий и временных блокировок. Manifest содержит размеры и SHA-256. Незавершённая копия получает `.partial` и не разрешает миграцию. Схема меняется транзакционно; повреждённая база или версия схемы выше 9 отклоняется.

Повторный запуск открывает существующее окно. Дополнительно блокируется параллельное открытие той же папки данных и проверяется процесс обычной Sfery. Старую версию нужно закрыть перед обновлением. Поведение старой версии при её повторном запуске во время работы новой отдельно не гарантируется.

Облачный `cloud-device.bin` читается через DPAPI текущего пользователя Windows без перезаписи; поддержаны строка токена и JSON с полем token. Реальный облачный обмен требует ручной проверки. Telegram использует восстановленный формат сессии: потребуется повторный вход; прежние файлы сохраняются в копии. Алгоритм отбора поручений реконструирован и может отличаться от исходного.

## Сборка и проверка

Нужны Node 24, Rust 1.99.1 MSVC и Microsoft C++ Build Tools. Из desktop запустить `./build-update.ps1` в PowerShell 7. Он проверяет публичный установщик 1.44.0 прежним ключом и SHA-256 извлечённого EXE, выполняет тесты, собирает NSIS без devtools. Результат — `dist/update-1.45.0`.

Actions устанавливает оригинал в одноразовом профиле runner, открывает синтетическую базу, обновляет установку через `/UPDATE`, сравнивает задачи и тему после запуска 1.45.0. Проверяются путь базы, версия в реестре, резервная копия и сохранённый старый EXE, повторный запуск и отсутствие второй работающей копии. Личные базы и приватные ключи в репозиторий не включаются.

## Новый ключ и подпись

Новый приватный ключ хранится отдельно от репозитория; открытая часть встроена в `tauri.production.conf.json`. Нельзя потерять его: нужна отдельная защищённая резервная копия. На компьютере владельца каталог ключа ограничен текущим пользователем и SYSTEM. Сам ключ не добавлять в Git или сообщения.

```powershell
./sign-update.ps1 -Installer ./dist/update-1.45.0/Sfery_1.45.0_x64-setup.exe -KeyPath C:/path/to/updater-v2.key
```

Пароль, если установлен, передаётся через `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Для будущих сборок Actions можно самостоятельно настроить secrets `TAURI_SIGNING_PRIVATE_KEY` и `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, затем запустить workflow с sign=true. Проверка Minisign/Ed25519 подтверждает соответствие подписи новому встроенному ключу. После неё создаётся `latest-v2.json`; старый `latest.json` копируется без изменения. Подпись обновлений не является подписью Windows Authenticode.

## Выпуск

Перед массовым выпуском проверить реальный вход Telegram и облачный обмен. Подготовить релиз v1.45.0 с установщиком, `.sig`, новым `latest-v2.json`, неизменённым старым `latest.json` и архивом для ручного перехода, содержащим установщик, Update-Sfery.cmd и MANUAL-UPGRADE.md. Публиковать только после проверки владельцем. Переход 1.44.0 выполняется запуском Update-Sfery.cmd; следующие версии обновляются автоматически по новому каналу.

## Откат

При обновлении через `/UPDATE` старый EXE сохраняется в `%LOCALAPPDATA%\local.sfery.planner\rollback\1.44.0`. Перед откатом закрыть Sfery и сделать отдельную копию текущих данных. Восстановить прежний EXE и файлы выбранной проверенной копии, кроме manifest.json, в прежнюю папку данных. Остаточные `planner.sqlite-wal`/`planner.sqlite-shm` нельзя оставлять рядом с восстановленной базой; маркер `.sfery-upgrade.json` также убрать перед следующим переходом на 1.45.0. Откат базы возвращает состояние на момент копирования, поэтому последующие изменения сначала сохранить отдельно. Автоматическое перезаписывание данных при откате не реализовано.
